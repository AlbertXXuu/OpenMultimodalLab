# 质量与开源标准

> `v1.0.0` 的公开证据见[发布准备矩阵](public-release-readiness.md)和
> [最终验证报告](reports/final-candidate-validation.md)。以下规则继续作为未来
> 版本的可复用门槛，复选框不是 v1.0 状态记录。

## 1. 代码质量

- 公共接口使用类型标注。
- 一个模块只承担一种主要职责。
- 适配器错误不能导致已完成结果丢失。
- 核心测试不依赖网络和大模型。
- 新增真实后端时必须保留 `mock` 离线测试路径。
- 修改数据格式时必须增加 `schema_version` 和迁移说明。
- PR 的 Python 3.11/3.12 矩阵必须通过测试、字节码编译和依赖一致性检查。
- 独立质量任务必须通过仓库文本/链接/JSON/隐私审计，成功构建 wheel，
  并在仓库外的新环境运行已安装 CLI。
- 远程 GitHub Actions 必须固定完整提交哈希；Dependabot 只提更新 PR，
  不绕过测试、人工审查或自动合并。

## 2. 实验质量

- 固定模型 revision，不只写模型简称。
- 保存生成参数和任务集版本。
- 可比较正式性能实验先执行恰好 1 次 warm-up，再执行 3 次完整重复。
- 区分模型加载、预处理、prefill 和生成时间。
- 报告中同时展示中心趋势和失败分布。
- 不能删除“不好看”的任务结果。

## 3. README 第一屏

正式发布前必须让读者在 30 秒内看到：

1. 项目解决什么问题；
2. 一张真实 Demo 或结果图；
3. 五分钟快速开始；
4. 支持哪些模型和输入；
5. 与类似工具的差异。

英文作为主 README，中文放在 `README.zh-CN.md` 或明确入口中。当前两份
README 已按相同证据和限制维护；后续修改用户可见命令时必须同步检查两者。

## 4. 降低贡献门槛

- `CONTRIBUTING.md` 给出环境和测试命令。
- Issue 模板区分 Bug、模型 Adapter 和数据任务。
- 使用 `good first issue` 标记小型任务。
- Adapter 有最小示例和契约测试。
- PR 必须说明测试证据和用户可见变化。

## 5. 发布节奏

- `v0.1`：基础评测闭环。
- `v0.5`：两个模型和多类输入。
- `v1.0`：完成全部必选验收项。

Release Notes 包括：

- 新能力；
- 破坏性变化；
- 实验结果；
- 已知限制；
- 升级或复现命令。

## 6. 提高传播概率

优先顺序：

1. 让用户能顺利运行。
2. 提供别人暂时没有的公平对比或低显存数据。
3. 用英文写清楚结果和限制。
4. 发布短演示和完整技术文章。
5. 在相关社区回答问题并收集反馈。

推广必须基于相关社区中的真实用例和可复现成果，禁止购买、交换或诱导式的
虚假互动。

## 7. 安全与隐私

- `.env`、密钥和本地路径不得进入 Git。
- 日志默认不保存私有媒体内容。
- 远程 API 后端必须明确提示数据会离开本机。
- 解析 PDF、视频和图片时限制文件大小和处理时间。
- 后续 Web 服务不直接信任上传文件名或 MIME 类型。

## 8. 每次公开版本前的检查模板

- [ ] 代码许可证明确。
- [ ] 模型与数据许可证兼容。
- [ ] README 命令从空环境验证。
- [ ] CI 通过。
- [ ] 没有密钥和个人路径。
- [ ] Demo 使用可公开媒体。
- [ ] 性能数字能追溯到原始记录。
- [ ] 已知限制可见。

## 9. 自动质量门槛

`scripts/check_repository.py` 使用 Python 标准库检查：

- 受支持文本是否为 UTF-8、无 BOM/尾随空格并以换行结束；
- Markdown 本地链接是否存在且没有越出仓库；
- JSON 与逐行 JSONL 是否能解析，JSONL 顶层是否为对象；
- GitHub Issue Form 是否包含必要结构；
- 远程 GitHub Actions 是否固定完整提交哈希；
- 常见 GitHub/OpenAI/AWS 凭据、私钥头和个人主目录路径。

CI 只在 `main` push 和 pull request 上触发，避免功能分支同时产生 push 与
PR 两份重复运行。并发组会取消同一 PR 的旧运行。质量任务与 Python
3.11/3.12 测试矩阵分离，使构建或仓库审计失败不会伪装成单元测试失败。
质量任务还会构建 wheel、在新虚拟环境安装，并从仓库外执行完整离线冒烟
路径。Python 与 GitHub Actions 依赖按上海时区每周检查并分组提交更新。
