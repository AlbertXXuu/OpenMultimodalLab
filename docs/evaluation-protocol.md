# Evaluation Protocol v1

This document defines how OpenMultimodalLab produces comparable and
reproducible benchmark results. A result is not considered publishable unless
the run records enough information to apply this protocol.

## 1. Scope

Protocol v1 covers inference-only evaluation of vision-language models on
versioned local task sets. It does not cover model training, fine-tuning,
human-preference leaderboards, or claims of state-of-the-art performance.

## 2. Dataset requirements

Every task must:

- use a supported `schema_version`;
- have a unique and stable task ID;
- declare its category, language, source, and answer format;
- reference media whose license permits repository distribution;
- contain a deterministic reference or scoring rule;
- remain unchanged after a dataset version is released.

If a task changes semantically, create a new task ID or dataset version instead
of silently replacing it.

## 3. Versioned synthetic dataset

`examples/tasks/synthetic-v1.jsonl` contains ten project-generated tasks:

| Category | Tasks | Purpose |
|---|---:|---|
| Image description | 2 | Color and shape recognition |
| Counting | 3 | Small-object counting with constrained answers |
| Spatial reasoning | 4 | Above, below, left, and between relations |
| Visual comparison | 1 | Relative size reasoning |

The corresponding PNG files are generated by
`scripts/generate_synthetic_images.py` using only the Python standard library.
This makes the media reproducible and avoids unclear third-party image rights.

`examples/tasks/synthetic-v1.1.jsonl` is the current corrected release. The
original file remains unchanged for auditability. Version 1.1:

- corrects a generated square that v1 labeled as a rectangle;
- makes constrained answer formats explicit in the affected prompts;
- declares one deterministic scorer for every task;
- records `metadata.dataset_version` so result files remain distinguishable.

Regenerate them with:

```powershell
.\.venv\Scripts\python.exe scripts/generate_synthetic_images.py
```

`examples/tasks/synthetic-docs-v1.jsonl` adds 32 schema 1.2 tasks over eight
project-generated images. It covers document OCR, document key-value lookup,
table QA, and chart QA. Each image supports four tasks, including direct
reading and derived arithmetic. Regenerate the assets with:

```powershell
.\.venv\Scripts\python.exe scripts/generate_synthetic_documents.py
```

The generator uses a bundled bitmap font and Python's standard library, so
asset bytes do not depend on host fonts or rendering-library versions. The
task set is released, but no formal real-model result on it is claimed yet.

## 4. Model identity

Each published run must record:

- model repository or provider;
- exact revision, tag, or immutable identifier;
- quantization format and bit width;
- inference backend and backend version;
- dtype and device placement;
- tokenizer or processor revision;
- any model-specific chat template.

A model family name without a revision is insufficient.

## 5. Input and prompt rules

- Use the task prompt exactly as stored.
- Do not manually rewrite prompts for individual failure cases.
- Record all system prompts and chat templates.
- Preserve the original media file.
- Record any resize, crop, frame sampling, color conversion, or compression.
- Do not compare models using different semantic information.

Backend-required formatting differences are allowed only when documented.

## 6. Generation configuration

The default deterministic profile is:

```text
temperature = 0
do_sample = false
max_new_tokens = task-specific, fixed before the run
batch_size = 1
```

If a backend cannot express one of these settings, record the effective
configuration and explain the difference.

## 7. Repetition and warm-up

- Use `--warmup 1` or more before performance measurement.
- Use `--repetitions 3` or more for every formal configuration.
- Keep task order fixed unless the run manifest records a seeded shuffle.
- Report medians for central tendency and p95 for latency tails.
- Do not discard slow, failed, or out-of-memory samples.

Warm-up attempts are stored with `phase: "warmup"` and remain auditable, but
they are excluded from score, latency, throughput, and failure aggregates.
Measured records use `phase: "measurement"` and a one-based `repetition`.

The current `mock` smoke runs are infrastructure checks and are exempt from
three-run model reporting because they do not measure a real model.

## 8. Timing boundaries

The native Transformers image-text adapters record the same fields:

- `model_load_ms`: dependency, processor, and weight loading;
- `media_load_ms`: opening media and converting it to RGB;
- `preprocessing_ms`: chat-template processing, tokenization, tensor creation,
  and device transfer;
- `input_tensor_shapes` and serializable native image-processor settings:
  auditable evidence of the effective model input representation;
- `ttft_ms`: synchronized `model.generate` start to completion of the first
  generated-token logits;
- `generation_ms`: synchronized wall time of the complete `model.generate`;
- `text_decode_ms`: generated token IDs to response text;
- `latency_ms`: adapter invocation plus deterministic evaluation in the runner;
- `peak_gpu_memory_mb`: maximum CUDA memory allocated during generation.

`output_tokens_per_second` counts generated token IDs, including terminal
special tokens, over `generation_ms`. `decode_tokens_per_second` excludes the
first generated token and divides by `generation_ms - ttft_ms`.

CUDA is synchronized at preprocessing, generation, and first-token boundaries.
The TTFT value is a local model-compute boundary, not network streaming time or
time until rendered text reaches an application.

Cross-family token throughput requires a tokenizer caveat: two tokenizers may
encode the same answer into different numbers of IDs. Use throughput for
repeated measurements within one model configuration. For cross-family
comparison, emphasize task quality, end-to-end task latency, TTFT, failures,
and peak memory, while publishing the raw token counts.

## 8.1 Run manifest

Every `oml run` writes `<output>.manifest.json` before inference starts and
finalizes it after the run. The manifest records:

- dataset and media SHA-256 values;
- selected task IDs, categories, dataset versions, and fixed order;
- backend, model ID, immutable revision, and generation parameters;
- warm-up count, repetitions, and metric boundaries;
- OS, Python, package versions, CPU, GPU, driver, and Git commit/dirty state;
- final status and the number of durable warm-up and measurement records.

Paths are repository-relative where possible. Inputs outside the repository
are represented by basename plus content hash so published manifests do not
leak personal absolute paths.

## 9. Scoring

Task schema 1.0 uses the legacy keyword evaluator, which measures
case-insensitive phrase coverage:

```text
matched expected phrases / total expected phrases
```

Task schemas 1.1 and 1.2 require an explicit `scoring` object. The current
deterministic scorers are:

- `normalized_exact_match` for single digits, one-word choices, and other
  prompts that explicitly constrain the complete answer;
- `attribute_groups` for locally bound attributes such as color plus shape,
  with optional expected-order enforcement;
- `numeric_tolerance` in schema 1.2 for a single numeric answer compared with
  a finite target and non-negative absolute tolerance;
- `keyword_coverage` only for backward-compatible schema 1.0 tasks.

Attribute groups are matched inside local answer units, not against the whole
response bag of words. This prevents “red square and blue circle” from
incorrectly satisfying both “red circle” and “blue square”.

The numeric scorer accepts signs, decimals, and comma-grouped numbers. A
response with zero or multiple numeric candidates scores zero, which prevents
an answer from passing by listing competing values. Manual review is allowed
only when deterministic scoring is impossible.

Model-as-judge scoring must never be mixed with deterministic scores without a
separate label and judge configuration.

## 10. Failures

Every attempted task must produce a record. At minimum distinguish:

- invalid task;
- missing media;
- model load failure;
- timeout;
- out of memory;
- generation failure;
- evaluation failure.

Failures remain in the denominator. A high score cannot cancel an unauthorized
side effect or a missing result.

## 11. Environment record

A published experiment must include:

- operating system;
- Python version;
- package or lockfile revision;
- CPU, GPU, driver, and available VRAM;
- relevant environment variables that are not secrets;
- Git commit SHA;
- dataset path and version.

Secrets, private paths, and user media must not be written into public reports.

## 12. Publishability checklist

Before sharing a comparison:

- [ ] Task set and media licenses are documented.
- [ ] Model revisions and generation settings are fixed.
- [ ] All configurations use the same semantic inputs.
- [ ] Each formal configuration has at least three runs.
- [ ] Raw JSONL records are preserved.
- [ ] Failures and exclusions are visible.
- [ ] Hardware and software environment are recorded.
- [ ] Claims match the metric actually measured.
- [ ] Known limitations are placed next to the result.
