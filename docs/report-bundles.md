# Deterministic report bundles

The single-run `oml report` command is useful for fast inspection. A public
benchmark needs a stronger artifact: one build that validates every source,
compares multiple backends on identical task grids, preserves failures, and
can be verified without running a model. `scripts/build_benchmark_report.py`
provides that release-oriented path using only the Python standard library and
the installed project package.

This tooling does not make the current 42-task corpus a final v1.0 benchmark.
It proves the report-rebuilding mechanism against the preserved image and
document results while the named video/robustness datasets and final
100-or-more-task runs remain open.

## Build the current evidence bundle

From the repository root:

```powershell
.\.venv\Scripts\python.exe scripts\build_benchmark_report.py `
  --input docs/reports/results/2026-07-31-qwen3-vl-comparison-formal.jsonl `
  --input docs/reports/results/2026-07-31-smolvlm2-500m-comparison-formal.jsonl `
  --input docs/reports/results/2026-08-02-qwen3-vl-docs-formal.jsonl `
  --input docs/reports/results/2026-08-02-smolvlm2-500m-docs-formal.jsonl `
  --output-dir runs/rebuilt-evidence
```

The order of `--input` arguments does not affect the generated bytes. Every
result must be inside the repository and have a same-stem
`.manifest.json` sidecar.

## Output contract

The output directory contains exactly six files:

| File | Purpose |
|---|---|
| `report.md` | Human-readable scope, run/category tables, evidence hashes, rebuild command, and limitations |
| `run-summary.csv` | One lossless aggregate row per dataset/backend run |
| `category-summary.csv` | Quality, reliability, latency, TTFT, throughput, memory, and response stability by category |
| `failures.csv` | Every failed measured attempt with task, repetition, status, and path-redacted error; header-only when there are no failures |
| `overview.svg` | GitHub-renderable visual summary derived from the same aggregates |
| `build-manifest.json` | Source, generator, and output sizes/hashes plus a deterministic self-hash |

The build has no current-time field and writes paths relative to the project
root. Rebuilding the same sources with the same generator code therefore
produces the same bytes on Windows and Linux.

## What is rejected

Before aggregation, each source must satisfy all of these checks:

- exactly one successful warm-up;
- exactly repetitions 1, 2, and 3, with each task appearing once per repeat;
- complete timing, TTFT, throughput, and peak-memory metrics on successful
  measurements;
- explicit status and error text for every failed measurement;
- no retry-attempt records and no measurement-phase model reload;
- one backend, model ID, and immutable model revision per result;
- deterministic decoding, batch size 1, and a completed clean-worktree
  manifest;
- matching JSONL/manifest counts and, when recorded by the manifest, matching
  result size/hash;
- current dataset and media bytes matching every manifest hash;
- at least two distinct backends on an identical task/repetition grid for
  every dataset included in the comparison;
- the same Git commit, task/media manifest, generation configuration,
  measurement protocol, OS/Python profile, processor, and GPU for all backends
  compared on one dataset.

Older preserved run manifests predate the output-hash and retry fields. They
remain accepted only when those fields are absent and the raw records
independently prove the stricter invariant. The new build manifest always
binds the exact legacy result and manifest bytes by SHA-256.

## Verify an existing bundle

```powershell
.\.venv\Scripts\python.exe scripts\build_benchmark_report.py `
  --verify `
  --output-dir runs/rebuilt-evidence
```

Verification checks:

1. the build manifest's deterministic self-hash;
2. the exact bytes and sizes of every source JSONL and sidecar manifest;
3. the exact bytes and sizes of all generator source files;
4. the exact bytes and sizes of all five derived outputs.

Changing a reported number, deleting a failure row, modifying an input, or
editing the generator after the build makes verification fail.

## Final v1.0 use

Once the repository owner approves the pending dataset and public-version
names, the final workflow is:

1. generate and human-review the canonical task corpus;
2. run both pinned models with the formal protocol on the complete corpus;
3. preserve each JSONL and completed sidecar manifest under
   `docs/reports/results/`;
4. build the final report bundle from those sources;
5. rebuild into a second empty directory and compare every byte;
6. run `--verify` during the final Windows and Linux validation passes;
7. record the final report bundle in the strict public-release readiness gate.

The generated report describes only the pinned task/model/hardware evidence.
It never infers a universal ranking, user preference, adoption, or GitHub Star
count.
