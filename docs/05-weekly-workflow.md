# 每周工作方法

## 1. 固定节奏

### 更新 A：功能

完成一个用户可以运行的纵向功能，例如“加载 10 条图片任务并用一个后端输出结果”。需要包含代码、测试和使用说明。

### 更新 B：实验

用固定配置运行实验，检查原始数据，写出结论和限制。不能只上传截图。

### 更新 C：文档或发布

更新 README、教程、变更日志和 Demo，或者发布一个带 Release Notes 的版本。

推荐安排：

- 周一：阅读和拆 Issue，不发布。
- 周二/周三：功能更新。
- 周四/周五：实验更新。
- 周末：文档、复盘和 Release。

## 2. 每次更新的 Definition of Done

一个更新只有同时满足以下条件才算完成：

- 解决一个明确的问题；
- 有可运行命令或可检查产物；
- 相关测试通过；
- 文档与实际行为一致；
- 没有提交密钥、模型权重和大型运行产物；
- 记录限制和下一步。

## 3. Issue 模板

每个任务先写：

```text
问题：
用户价值：
范围：
不做什么：
实现方案：
验收命令：
完成证据：
风险：
```

任务预计超过 6 小时时，应拆成多个独立可验证的 Issue。

## 4. 实验记录模板

```text
实验问题：
模型与 revision：
任务集版本：
硬件与软件环境：
生成参数：
重复次数：
原始结果：
主要发现：
失败样本：
限制：
下一步：
```

## 5. 周复盘

每周末只回答五个问题：

1. 本周新增了什么用户可见能力？
2. 哪条命令证明它能运行？
3. 哪个假设被数据支持或否定？
4. 当前最大的技术风险是什么？
5. 下周唯一最重要的出口条件是什么？

## 6. 学习与实现比例

建议使用 `30% 学习 + 60% 实现 + 10% 复盘`。连续阅读多篇论文但没有形成代码、实验或决策，不计入项目进展。

## 7. Git 提交建议

提交应描述结果，例如：

- `feat: add versioned JSONL task loader`
- `test: cover duplicate task identifiers`
- `docs: define fair latency measurement protocol`
- `fix: preserve completed records after adapter failure`

避免 `update`、`week 1`、`try again` 等无法说明变化的提交标题。
